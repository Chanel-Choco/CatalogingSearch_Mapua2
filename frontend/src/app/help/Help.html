System Overview

The Cataloging Search Resources Platform is a web-based application for the Mapúa University Library (Makati Campus). It centralizes bibliographic searching, enabling librarians and student assistants to locate, review, and pin book records for efficient cataloging.

1.1 What You Can Do

  • Search for books by ISBN, Title, or Author
  • Retrieve aggregated bibliographic metadata from multiple reliable sources
  • Pin records to the system database for cataloging reference
  • Edit and manage pinned bibliographic records
  • Monitor search activity through audit logs

Searching for Books

The Home page is your primary workspace. The system supports partial matching — you do not need a complete title or full author name.

3.1 Search Methods

ISBN

Enter a 10- or 13-digit ISBN. Best for identifying a specific edition.

Title

Enter part or all of a book title. Partial matching is supported.

Author

Enter a full or partial author name to retrieve all books by that author.

3.2 How to Search

  1. Select your preferred search method (ISBN, Title, or Author).
  2. Type your keyword into the search field.
  3. Click Search or press Enter.
  4. Wait for results — the system queries all sources simultaneously.
  5. Browse result cards showing title, author, publisher, year, and summary.

3.3 Understanding Results

  • Multiple entries for the same book may appear from different sources.
  • Detail level varies depending on which source returned the record.
  • A Cutter Number is automatically generated for classification.
4

Pinning a Book Record

Pinning saves a bibliographic record into the database, making it available in Pinned Books for cataloging reference and further editing.

  1. Search for a book using the Home page.
  2. Click the Pin button on the desired result card.
  3. A confirmation message will appear — the record is now saved.
  4. Access it anytime from the Pinned Books page.
Note: Both Admin and Student Assistant roles can pin records.
5

Pinned Books

5.1 Viewing Pinned Records

  1. Navigate to Pinned Books from the sidebar.
  2. All saved records are displayed — click any to view full details.

5.2 Editing a Pinned Record (Admin only)

  1. Go to Pinned Books and find the record to update.
  2. Click Edit, modify the fields, then click Save.
  3. A confirmation appears and the audit log updates automatically.

Search Logs

Navigate to Search Logs from the sidebar to view all recorded queries including search term, type, date, and user who performed the search.

6.1 Deleting Logs (Admin only)

Delete a single entry
  1. Click Delete next to the entry.
  2. Confirm when prompted.
Delete all entries
  1. Click Delete All at the top.
  2. Confirm the action.
Note: Deleting logs does not affect pinned records — they are stored separately.

7.2 Changing Your Password

System Limitations

  • Authentication: User accounts must be manually created by an administrator. Mapúa SSO integration is not yet implemented.
  • Desktop-Optimized: Designed for desktop browsers. Mobile responsiveness is limited.
  • No Borrowing Integration: Focuses solely on bibliographic search and cataloging — no borrowing or return management.

System Overview

Current Situation and Challenges

The University Library currently uses an existing cataloging system (Ex-Libris) to retrieve book information using the ISBN or title of a book. Although the system is in place, it does not always successfully identify or display complete book information. In some cases, entering the ISBN or title returns no results or only shows partial details.

Because of these limitations, library staff must search multiple external sources and open several tabs to gather missing information such as book summaries, content notes, LCCN, and author cutter numbers — making the cataloging process time-consuming and inefficient.

Why This Platform Is Needed

The system will serve as a centralized information-finding platform where all required bibliographic data can be accessed in one place. Instead of manually searching across different websites, the system retrieves and presents book information using a single search based on ISBN, title, or author — allowing library staff to copy accurate and complete information into the existing library backend without switching between multiple sources.

High-Level Objectives

  1. Provide accurate and complete book information using ISBN, title, or author search.
  2. Centralize book information retrieval from multiple trusted external sources.
  3. Reduce the time and effort required to search for book details.
  4. Improve accuracy and consistency of cataloged book information.
  5. Support the growing library collection as new courses and materials are added.
  6. Offer a user-friendly, desktop-based interface aligned with the Mapúa Library website design.

Stakeholder Identification

Librarians

Responsible for cataloging library materials, managing bibliographic records, and ensuring accurate book information is entered into Ex-Libris (Ms. Carla Rosario). Their main concern is search reliability and accuracy.

Student Assistants

Support librarians by searching and gathering bibliographic information. Their primary concern is ease of use and avoiding mistakes when copying data. Expect partial matches and role-based access restrictions.

Faculty Members

Indirect stakeholders who rely on accurate and timely availability of library materials to support teaching and research. Concerned that inaccurate cataloging may affect access to learning resources.

Library Administrators

Oversee library operations, policies, and long-term planning. Expect system sustainability, scalability, and alignment with institutional standards including Mapúa email authentication.

University IT Staff

Provide technical support, system maintenance, security, and integration. Concerned with security, maintainability, and compatibility with current IT infrastructure.

External Data Providers

Platforms such as Library of Congress, WorldCat, Amazon Books, Goodreads, and Cutternumber. Their concern is data availability and consistency, as system accuracy depends on these sources.

Requirements Gathering

Requirements were gathered primarily through an interview with the client. A permission letter was sent on January 12, 2026 to request approval to conduct an interview with Ms. Carla Rosario (head cataloger). The interview was conducted on January 15, 2026 and was recorded with permission. The team also observed the current system, took pictures, and wrote notes.

Gathered Raw Requirements

  1. The system must allow searching by ISBN, book title, and author name, with support for partial matches.
  2. Entering an ISBN or title should display complete book information in one place.
  3. The system should include both physical books and e-books.
  4. Each book record should contain ISBN, title, author name, Cutter Number, LCCN, summary, and content notes (if available).
  5. Book information should be retrieved from Library of Congress, WorldCat, Amazon Books, Goodreads, and a Cutter Number website.
  6. Only library staff and student assistants are allowed to use the system.
  7. Users must log in using their myMapúa email, with Admin and Student Assistant access levels.
  8. The system should be easy to use, follow the Mapúa Library website design, and be used on desktop computers only.
  9. The system should be fast and accurate, and support automatic backup and future system integration.
  10. Reports and analytics are not required. The system is considered successful if it meets Ms. Rosario's requirements.

Requirements Analysis

4a. Functional Requirements

Authentication & Access
  • FR-1.1: The system shall authenticate users via official Mapúa email to restrict access to authorized staff and student assistants only.
  • FR-1.2: The system shall differentiate between Admin (Ms. Rosario) and User (Student Assistant and Staff) roles to control access to sensitive logs.
Metadata Retrieval and Consolidation
  • FR-2.1: The system shall allow users to search for book information using an ISBN, Title, or Author.
  • FR-2.2: The system shall support partial matches and keyword searches for titles and authors.
  • FR-2.3: The system shall automatically fetch metadata (Title, Author, Author Number, LCCN, Summary, and Content Notes) from integrated sources and display them on a single results page.
Record Management (Create, Update, Delete)
  • FR-3.1: The system shall allow users to "Pin" (save) fetched book information into the local database for future reference.
  • FR-3.2: The system shall allow users to manually edit any field of a pinned book to ensure data accuracy.
  • FR-3.3: The system shall allow users to remove (unpin) book records from the local repository.
Administrative Audit and Logs
  • FR-4.1: The system shall automatically record a History Log of every search, including the query, user ID, and timestamp.
  • FR-4.2: The system shall allow the Admin to view and delete search history logs through a private dashboard.

4b. Non-Functional Requirements

Security

Secure database for Mapúa email verification. Admin Dashboard and global logs must be inaccessible to Student Assistant accounts.

Availability

Web-based desktop tool accessible both within the Mapúa campus network and via remote login from home.

Performance

Retrieve and display metadata from external APIs within 5 seconds per query. Local database must retrieve Pinned Books in under 1 second.

Usability

UI must follow the Mapúa Library website color scheme and layout. Optimized for desktop screen resolutions to allow efficient copy-pasting of large text blocks.

Scope of the System

Will Include
  • Book search by ISBN, Title, and Author (partial matches supported)
  • Bibliographic information retrieval: title, creator, subjects, ISBN, ISSN, publication year, material type
  • Integration with Library of Congress, WorldCat, Amazon Books, Goodreads, and Cutter Number database
  • User account management with Admin and Student Assistant roles
  • Mapúa email-based authentication
  • Desktop-only interface aligned with Mapúa Library design
  • Optional automatic backups and basic data recovery
Will Not Include
  • Book borrowing, returning, or renewal processes
  • Overdue notifications or fine computation
  • Inventory management and auditing
  • Statistical reports on library usage
Note: The system is strictly a support tool for cataloging — not a full Library Management Information System (LMIS).
6

Limitations of the System

  • Circulation and Borrowing Management: The system will not track book loans, returns, or borrowing history.
  • Mobile Application Support: The system is optimized for desktop environments only, as requested by the client for heavy data entry and copy-paste workflows.
  • Physical Book Digitization: No features for scanning physical pages or OCR. Relies entirely on existing digital metadata from external APIs.
  • Online Payment Processing: No functionality for handling library fines, fees, or financial transactions.
  • Real-time Inventory Tracking: The system will not reflect real-time book availability (e.g., "On Shelf" or "Checked Out").
  • Public Access: Restricted to library staff and student assistants — not accessible to the general student body or faculty.

Design Overview

The Cataloging Search Resources Pages/Platform is a centralized bibliographic data retrieval system designed to streamline the cataloging process by aggregating book metadata from multiple external sources into a single interface — eliminating the inefficiency of manual, multi-tab searching.

Centralized Metadata RetrievalSingle-query search via ISBN, Title, or Author
Multi-Source AggregationLOC, WorldCat, Amazon, Goodreads, Cutter Number
Role-Based Access ControlStudent Assistant view vs. full Admin view
Pin and Edit Staging AreaSave and edit records before entry into Ex-Libris

Core Design Goals

Efficiency

Retrieve complete book details in under 15 seconds per query. Desktop-optimized for heavy text manipulation and copy-pasting workflows.

Visual Consistency

Interface aligned with the existing Mapúa Library website design to minimize the learning curve.

API Modularity

Each external data source connection is isolated so changes in one platform do not disrupt the entire system.

Security & Reliability

Critical functions strictly limited to the Admin role. System degrades gracefully — if one source is offline, others continue.

Design Assumptions

  • The system will be accessed exclusively via desktop computers within the library or authorized remote workstations.
  • A stable internet connection is available to fetch real-time data from external APIs.
  • The system acts as a supplement to Ex-Libris, not a replacement — no borrowing or financial data will be processed.
  • Users possess the technical literacy to interpret bibliographic data and manage clipboard operations (copy-paste).
  • The "Pinning" feature is intended for temporary reference during the cataloging shift, not for permanent long-term archival.

System Architecture Design

2.1 Selected Architecture Type

The system uses a layered client-server architecture with a web-based deployment model. It is layered because it separates concerns into presentation, application, and data layers to improve maintainability, scalability, and security.

2.2 System Components and Layers

2.3 Deployment Overview

2.4 Justification of Architectural Decisions

The system integrates with multiple trusted sources — Library of Congress (primary), WorldCat, Amazon Books, and Goodreads — using APIs to automatically fetch key book data. LOC is prioritized as the primary source since it contains most of the information needed, while Amazon and Goodreads provide summaries and content notes. In cases where API data is unavailable, the system can perform web scraping (in compliance with each site's terms of service). All collected data is organized in a MySQL database and presented via an Angular web interface.

Data Design

The data design uses a normalized relational database structure, separating core book data from extensive metadata and author details to ensure data integrity and scalability.

4.1 Major Entities and Key Attributes

User
  • user_id (PK), mymapua_email, full_name, role (Admin/StudentAssistant), created_at
Book
  • book_id (PK), isbn, title, publication_year, publisher, material_type, series, format
Author
  • author_id (PK), author_name, cutter_number
Book_Author
  • bridge_id (PK), book_id (FK), author_id (FK) — Many-to-Many bridge
Bibliographic_Metadata
  • metadata_id (PK), book_id (FK), lccn, summary, content_notes, subjects, source, retrieved_at
Pinned_Book
  • pinned_id (PK), book_id (FK), pinned_by_user_id (FK), pinned_at, status (Pending/Reviewed/Ready_For_Export)
Search_Log
  • log_id (PK), query, performed_by_user_id (FK), timestamp, target_isbn
Record_Activity
  • activity_id (PK), action_type (PIN/UNPIN/DELETE/VIEW), book_id (FK), executed_by_user_id (FK), timestamp

4.2 Relationships

  • User → Pinned_Book (1:M): A single user manages many pinned books (the staging workspace).
  • Book → Pinned_Book (1:M): A book can be pinned by multiple users working collaboratively.
  • Book → Bibliographic_Metadata (1:1): Each book has detailed metadata linked to it, keeping the Book table light and fast.
  • Book ↔ Author (M:M via Book_Author): A book can have multiple authors; an author can write multiple books.
  • User → Search_Log (1:M): Tracks all search queries generated by a user.
  • User → Record_Activity (1:M): Tracks every specific interaction (Pinning, Deleting) a user performs.
  • Book → Record_Activity (1:M): Tracks the history of a specific book record.

Design Constraints and Assumptions

6.1 Design Constraints

  • Web-based desktop-only access: The client specified desktop-only use by librarians. Responsive mobile design was intentionally excluded to reduce complexity.
  • Technology stack limitations: Constrained to Angular (frontend), Spring Boot (backend), and MySQL (database) as approved in the previous phase.
  • API usage policies and scraping restrictions: Some external sources impose request limits or restrict web scraping. Official APIs are prioritized; web scraping is a last resort only when compliant with terms of service.
  • Data integrity and academic use: Accuracy of bibliographic data is critical. This influenced the decision to prioritize authoritative sources such as the Library of Congress over commercial platforms.
  • Limited development timeframe: Due to academic project deadlines, complex features such as machine learning recommendations or full-text indexing were excluded.

6.2 Design Assumptions

  • Librarians have basic computer literacy and are familiar with cataloging workflows.
  • A stable internet connection is available to access external APIs.
  • External APIs will continue to provide consistent data formats.
  • The volume of concurrent users is relatively low — intended for internal library staff use.
  • Security requirements are limited to authentication and controlled access, as no sensitive personal data is heavily processed.

Design Readiness for Development

7.1 Alignment with Approved Requirements

The system design directly supports the approved requirements by: allowing searches by ISBN, title, or author; automatically retrieving and organizing bibliographic information from trusted sources; generating Cutter Numbers internally; storing and retrieving book data efficiently using a relational database; and presenting results through a clear, structured web interface.

7.2 Implementation Feasibility

The layered architecture clearly separates responsibilities — Angular handles user interaction, Spring Boot manages business logic and API integration, and MySQL ensures persistent structured data storage. This separation allows developers to work on different components in parallel.

7.3 Risks and Areas for Clarification

  • Final confirmation of API access limits and authentication requirements
  • Detailed rules for Cutter number generation
  • Error-handling behavior when all external data sources fail
  • Data update policies (when and how book data should be refreshed)
Overall Readiness: The system design is well-defined, feasible, and aligned with the project scope. The architecture, constraints, and assumptions have been carefully considered, making the design suitable to proceed to the development phase with minimal risk and clear implementation guidance.
